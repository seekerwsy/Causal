\section{Motivating Example and Problem Formulation}

\subsection{Multi-Operation Scope Disambiguation}

Consider a natural-language task that stores an uploaded file's path in a SQL
database and subsequently uses the same path to serve file downloads
(Figure~\ref{fig:method-example}). The prompt mentions one data object
(\texttt{filepath}) participating in two distinct operations: SQL persistence and
filesystem retrieval. A developer considering adding a SQL parameterization
requirement needs to know which operation and input role the edit constrains,
which non-target behaviors (saving uploads and downloading files) must remain
invariant, and what empirical effect the edit produces. Attaching the requirement
to the download operation instead of database storage would define an entirely
different intervention.

\prompttsg records these task-local distinctions so that requirement assessment
and prompt realization operate on the same scoped object. An atomic
requirement hypothesis fixes the target requirement expression, governed
operation and object-component path, execution conditions, edit operator
(Requirement Introduction $\mathcal T_r^+$, Requirement Withdrawal
$\mathcal T_r^-$, or explicit policy restatement), and preserved non-target
obligations. The experimental unit is this concrete prompt-editing policy, not
an intrinsic causal property of an isolated keyword or graph node.

\subsection{Target Causal Estimand and Endpoint Separation}
\label{sec:matter-definition}

We estimate population-level intervention effects on independent, deduplicated
\emph{task units} within a declared task population and generator model;
repeated generations from the same task unit reduce within-task noise without
inflating effective sample size. The primary safety endpoint is
\emph{oracle-evaluable secure-code yield}:
\begin{equation}
  Y = Y_C Y_E\,\mathbb I\{\text{Oracle label is secure}\},
  \label{eq:secure-yield-pf}
\end{equation}
where $Y_C \in \{0,1\}$ indicates valid parseable code and $Y_E \in \{0,1\}$
indicates that an arm-blind security Oracle renders a supported decision.
Functionality preservation against the original task, code validity $Y_C$,
Oracle evaluability $Y_E$, \texttt{unknown} security coverage, and joint
secure-and-functional success remain separately reported outcomes. Neither
\texttt{unresolved} source facts nor \texttt{unknown} Oracle decisions are
coerced into absence or insecurity.

Under assigned-arm intention-to-treat (ITT) accounting, every committed task
assignment remains in its assigned arm regardless of post-assignment fidelity,
formatting errors, or non-target drift. For a single-requirement policy $h$,
a confirmed positive-meaningful finding supports scoped security hardening,
whereas a negative-meaningful finding yields an endpoint-specific warning;
positive hardening yield and adverse warnings are tracked separately in guidance
generation. Adoption recommendations additionally require meeting declared
task-preservation and Oracle-coverage criteria.
