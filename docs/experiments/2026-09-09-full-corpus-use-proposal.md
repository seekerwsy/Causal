# 尽量利用全部 2,165 个任务的方案

日期：2026-09-09。状态：基于已核验来源的设计建议，尚未修改活动协议、质量标签或正式角色。

建议将现有 2,165 个任务作为完整研究语料，逐任务明确其可支持的表示、干预和测量用途。最有价值的调整是：先扩展已经通过质量审查的任务，再评估候选级的说明充分性，逐步支持多语言。主效应样本量继续按候选的独立任务计算。

这需要前瞻修订来源准入与候选资格的接口，以及相应测量实现。它不能通过直接降低质量、Oracle 或统计阈值完成，也不能将既有冻结包解释成已经通过新规则。

## 2. 将全局质量结论与候选的使用权限分开

建议保留所有原始来源与质量结论，在现有候选资格记录中分别回答下面的问题，形成同一条研究路径上的准入决定。

| 要判定的问题 | 可使用的依据 | 不充分时的处理 |
|---|---|---|
| 哪些源语义事实能被可靠表示？ | 精确原文及原始可见资产，合格的抽取与原文证据 | 相关事实明确为 UNRESOLVED，不能改为 ABSENT |
| 任务能否接受当前候选干预？ | 上下文、目标状态、操作条件、兼容性、非目标约束与完整臂定义 | 阻断该任务与候选的组合，不自动宣布其对所有候选无用 |
| 当前安全目标能否独立测量？ | 目标、输入来源、运行语义、独立 Oracle 及其资格范围 | 不授予目标安全解释；保留相应不可测或未知状态 |
| 功能与联合成功能否判定？ | 有来源依据的完整要求、相关原生测试及独立测量资格 | 对无法判定的内容保留 UNKNOWN，不以局部要求通过代替完整功能成功 |

所有任务进入某个确认候选的决定都必须发生在分配与生成结局之前。分配后，安全、功能、Oracle 未知、无代码和失败继续按原 ITT 规则保留；不能再按输出是否容易评价筛任务。

这里的关键修订是：**来源说明不完整时，允许经过独立资格验证的、边界充分明确的任务—候选组合进入相应分析。** 若缺失信息涉及干预要改变的安全边界、待保持的关键行为或测量目标，仍应阻断。

一个说明性例子：任务明确要求使用 SQLite，根据外部输入值查询固定表，但没有约定最终结果格式。若查询语义、目标控制和不变条件足够明确，可以评估值参数化策略的安全产出；完整功能正确性可能仍不可判定。若输入是否进入 SQL、操作对象或允许的查询行为本身也不明确，则不能靠猜测建立候选。这是方法边界示例，不是对任何真实任务的新审查结论。

现有 `measurement.py` 已有功能 UNKNOWN 状态，`outcomes.py` 也能同时保留安全产出和未知功能/联合成功。这提供了结果表达基础；候选级准入规则、功能判定权限和资格证据仍需前瞻定义与验证。不能只改变质量过滤条件就开始运行。

## 3. 分别使用三类来源任务

### 质量通过的 720 个：优先扩大有效研究范围

先在现有 Python 工具链中审查全部 853 个 Python 来源，优先完成其中 381 个质量通过任务的范围覆盖。其保护角色后的上限为 306，当前 151 个范围外任务应获得明确的候选适用或不适用决定。

来源 CWE 用于出处和类别记录，具体候选必须依据源语义与前瞻冻结的适用范围。允许候选跨来源 CWE 时，应明确写入目录和资格计划，并验证覆盖；不能事后根据出现了更多可用特征或更好的结果扩大范围。

随后评估非 Python 的 339 个质量通过任务，保护已有角色后剩余 332。可先比较 JavaScript 的 54 个任务与 C/C++ 的 130 个任务所需的安全机制、运行上下文和测量开发工作，再决定接入顺序。

多语言沿用相同的表示—优先级—假设冻结—干预/随机化—测量—结局组装—推断七阶段和 ITT。语言差异由明确的解析、干预及测量实现承担，不建立九套独立实验框架。不能将任务翻译成 Python 后作为原语言任务，也不能把同一任务的语言变体计成独立样本。

当前 `measure_generated_code` 的语法判定仅支持 Python，因此九语言尚未实现。CodeQL 官方文档列出了 C/C++、C#、Go、Java、JavaScript、Python、Rust 等语言支持，可作为部分测量开发的候选工具；其语言支持列表不能替代本项目具体 Oracle 的有效性验证，未检出告警也不能直接等同安全。[官方支持表](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)

### 说明不足的 1,284 个：复核具体用途，而非整体改为合格

其中 1,283 个有非空功能要求，180 个有来源测试引用，420 个为 Python。这些是值得继续检查的入口，但无法据此给出可恢复比例。

建议对未暴露、未预留的 **1,245 个**，在统一且结果盲态的新规则下判断：

1. 是否只是当前流程漏导了原任务本来提供的上下文或资产。只能补回可核验的原始材料，重新冻结输入身份，并保留原任务谱系；这种恢复不增加独立单位数。
2. 对哪些候选，现有说明已经足以界定干预、非目标约束和安全测量。合格组合可以进入相应前瞻分析，其他维度保留未知。
3. 若只足以表达部分提示语义，可用于明确冻结的表示资格或未知处理检查，不能生成猜测性的安全结局。

原生测试只能用于其真实覆盖的要求；需要区分功能断言与安全断言，不能把上游测试中的额外安全要求偷偷写入所有臂的功能标准。

补写需求、由模型臆造缺失接口、从参考答案反推新要求、扩写提示或制造自然特征状态都会改变任务。它们不能被包装成恢复原有自然任务，也不能用于 D0 填满四格。

### 来源缺陷的 161 个：保留其来源修正或明确失效用途

其中 160 个未暴露且未预留。只有存在可核验的原始材料或审查错误证据时，才考虑重新审查；旧冻结结论保持不变。

无法建立一致任务语义的记录，可用于事先定义的资格检查，例如识别原文冲突、报告无法判断、避免补造要求。这些检查沿用现有资格或工程诊断责任，未经相应冻结不支持新的论文效果主张。无法定义干预或结局的记录不进入主效应估计。

扣除现有暴露和预留后，即使先忽略所有质量、语言与候选条件，剩余也只有 2,043 条来源任务、2,042 个独立组上限。这个数字仅说明角色与独立性边界，不能用作样本量目标。

因此，利用率应分别报告：来源是否有明确处置、是否支持某种合格表示/诊断，以及每个确认候选真正拥有多少独立任务。不能以一张完整清单替代主效应的信息量，也不能以增加不适用、不可测的任务来宣称功效提升。

## 5. 推荐的实施顺序与必要修订

1. **先统一定义候选级充分性规则。** 明确哪些缺失妨碍干预，哪些只限制功能结论，哪些使安全解释不可用。开发材料与独立验收材料继续隔离；使用任务级反馈改方法后必须记录暴露。
2. **先处理现有 Python 的 853 个来源。** 优先评估额外 151 个质量通过任务的范围，再复核 420 个说明不足任务的候选用途。先建立可核验的实际容量，不把 853 写成实验 N。
3. **在同一路径中逐种加入非 Python 测量。** 每次先验证最小代表实例，冻结语言/任务范围与资格证据，再规模化处理；多语言安全含义和功能测量必须分别成立。
4. **对全库完成来源用途处置与独立性核验。** 对修复输入、同源任务、角色预留和未决状态保持可追溯记录；不直接翻转 v5 的质量标签。
5. **根据实际候选支持完成正式设计。** 保持 Pair 独立准入和自然四格要求；使用实际任务重叠进行功效与预算规划。若汇总不同语言的效果，须事先定义共同策略含义、目标总体、权重和多重性规则；语言差异的推断仍受上下文修饰规则约束。

来源覆盖扩展、候选准入变化和多语言都需要新一轮前瞻资格/设计冻结。正式假设选择名额、实际意义阈值及功效要求不能由审查或实验结果反向调低。已发现的家族推断失效问题也仍需单独修订和校准，数据增多不能替代那项工作。

建议将上一轮外部来源审查排在这轮内部利用审查之后。先看已有 2,165 个任务在新规则下能提供哪些实际候选支持，再为仍缺失的领域定义独立自然任务补充目标；D0 仍受单轮、盲态、冻结范围及只补 Discovery 的约束。

在实现上复用现有来源表、候选资格、测量结局、角色冻结和实际支持功效路径。需要修改规则的地方同步更新独立验证器；无需另建数据平台、分析框架或并行活动方法。
